# START HERE — проект «Розница»

Этот файл задаёт обязательный порядок старта проекта в любом новом чате/агенте.

## Триггер
Если пользователь пишет что-то вроде:
- «Продолжаем Розницу»;
- «Работаем по Рознице»;
- «Продолжаем закупки/подбор по Рознице»;
- или явно ссылается на репозиторий `KVAKUSK/roznitsa-procurement-control`,

не начинать подбор по памяти и не просить пользователя пересказывать правила.

## Обязательный порядок действий
1. Прочитать `context/HANDOFF_CURRENT.md` в этом репозитории.
2. Прочитать `context/ERRORS_AND_LESSONS.md` — журнал подтверждённых ошибок и автоматических защит.
3. Найти в Library `/работа/РЕГЛАМЕНТ РОЗНИЦА ЗАЯВКА_актуальный.docx` и прочитать актуальный регламент целиком.
4. Прочитать Airtable: база `Закупки — подбор и контроль`, таблица `Подтвержденные решения`, учитывать активные решения со статусом `Подтверждено Леной`.
5. Прочитать `rules/price_source_manifest.json` и получить ПОЛНЫЙ фактический список файлов Library `/работа` через листинг папки, а не через семантический поиск.
6. Выполнить source preflight из `scripts/source_registry.py`: каждый разрешённый прайс из manifest обязан физически присутствовать в `/работа` и быть синхронизирован в полном поисковом индексе. Если хотя бы одного разрешённого файла нет в индексе — подбор ЗАПРЕЩЁН до синхронизации.
7. Найти актуальный рабочий Excel из Library, указанный в handoff, и работать только после шагов 1–6.
8. Текущие цены, поставщика, наличие и вложимость подтверждать по исходной строке актуального прайса. История и Airtable — правила/индекс/подсказки, но не замена сырому прайсу.

## Механизм поиска товара
Семантический поиск Library — только вспомогательный инструмент и НИКОГДА не считается полным каталогом.

Правильный порядок:
1. Полный реестр источников `rules/price_source_manifest.json`.
2. Полный синхронизированный индекс Airtable по всем разрешённым файлам.
3. Поиск кандидатов по всему этому набору, а не по нескольким первым релевантным файлам.
4. Для выбранного кандидата обязательная перепроверка исходной строки сырого прайса: название, поставщик, цена, единица цены, вложимость, остаток.
5. Только после полного поиска допускается переход к более далёкому аналогу.

Запрещённый паттерн: `семантический поиск ничего не показал → считать товара нет → брать аналог`.

## Приоритет источников
При противоречиях использовать такой порядок:
1. Явное новое указание Лены в текущем чате.
2. Активное подтвержденное решение Лены в Airtable.
3. Актуальный регламент из Library.
4. `context/ERRORS_AND_LESSONS.md` и автоматические regression tests.
5. `context/HANDOFF_CURRENT.md` как состояние проекта и навигация.
6. `rules/price_source_manifest.json` как детерминированный реестр актуальных прайс-файлов.
7. Исторические листы/предыдущие заявки как подсказка.
8. Автоматическое предположение ассистента — только как кандидат, не как подтвержденное правило.

## Ключевой принцип накопления знаний
Если Лена при проверке говорит, что вариант подходит, не подходит, относится/не относится к категории, указывает правильного производителя/поставщика/формат/массу или формулирует общее правило — это нужно занести в Airtable `Подтвержденные решения` и, если правило формализуемо, в `context/ERRORS_AND_LESSONS.md` + regression test.

Если замечание по смыслу общее, не ограничивать его конкретным брендом или строкой. Например, запрет использовать один и тот же удобный аналог для большого числа разных запросов относится ко всем категориям, если ассортимент позволяет подобрать несколько разных подходящих вариантов.

## Что нельзя делать
- Нельзя начинать новую работу только по памяти чата.
- Нельзя считать handoff заменой регламента.
- Нельзя считать Airtable заменой актуального прайса.
- Нельзя использовать неполный Airtable как доказательство отсутствия товара.
- Нельзя считать результат семантического поиска Library полным списком прайсов.
- Нельзя продолжать подбор, если source preflight обнаружил несинхронизированный разрешённый прайс.
- Нельзя автоматически превращать собственное предложение ассистента в подтвержденное правило без подтверждения Лены.

Этот файл — постоянная точка входа. `context/HANDOFF_CURRENT.md` содержит текущее состояние проекта и может обновляться по мере работы.
